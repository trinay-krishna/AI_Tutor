# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

AI_Tutor is an AI tutor for learning software technologies. Admins onboard technologies (React, FastAPI, Docker, ...) and documentation URLs; the backend ingests each URL into a technology-scoped vector store. Learners pick a technology and chat with a RAG tutor that answers from that technology's resources, falls back to general software knowledge for related topics, and declines anything unrelated. It can also generate study plans grounded in the onboarded resources.

Two services: a FastAPI backend (`backend/`) and a React + Vite frontend (`frontend/`), plus a Postgres + pgvector database (`db`, via Docker Compose).

## Architecture

- **backend/** — Python FastAPI app managed with `uv`. Entry point is `backend/src/main.py` (`src.main:app`).
  - `src/config.py`, `src/db.py`, `src/models.py`, `src/schemas.py`, `src/deps.py` — settings, async SQLAlchemy engine, ORM models, Pydantic schemas, FastAPI dependencies.
  - `src/routers/` — `auth`, `technologies`, `resources`, `retrieval`, `conversations`, `health`.
  - `src/services/` — `security` (password/session hashing), `slugs`, `llm` (ChatOpenAI/OpenAIEmbeddings factories), `vector_store` (langchain-postgres `PGVectorStore` bound to our own `chunks` table), `retrieval`, `chat`, `prompts`, `study_plan`.
  - `src/services/ingestion/` — `fetcher` (SSRF-guarded HTTP fetch + robots.txt), `extractor` (trafilatura → markdown), `splitter` (LangChain text splitters), `pipeline` (fetch→extract→split→embed→store, build-then-swap).
  - `src/services/tutor_graph/` — the LangGraph tutor graph: `state.py` (TypedDict state), `schemas.py` (structured-output Pydantic models), `nodes.py`, `graph.py`. Flow: `classify → {refuse | retrieve → generate_answer | build_outline → generate_plan → validate_plan}`.
  - `src/scripts/` — `create_admin`, `promote_user`, `eval_scope` (classifier accuracy eval against `backend/evals/scope_cases.yaml`).
  - `alembic/` — migrations (Postgres + pgvector; the `chunks` table is hand-written, not auto-generated by PGVectorStore, so it keeps real FKs and cascading deletes).
- **frontend/** — React 19 + Vite, plain JSX, `react-router` for routing. `src/auth/` (session context + route guards), `src/pages/` (learner + admin pages, chat), `src/components/` (`MessageBubble`, `SourceList`, `NavBar`), `src/api.js` (fetch wrapper, same-origin via the Vite dev proxy).
- **db** — `pgvector/pgvector:pg17`. The `chunks` table is both a normal SQLAlchemy-managed table (FKs to `technologies`/`documents`/`resources`, HNSW index) and the table `langchain_postgres.PGVectorStore` reads/writes.
- `docker-compose.yaml` wires `db`, `backend` (localhost:8000, proxied from container port 80), and `frontend` (localhost:5173). Both `backend`/`frontend` mount their local source dir for live reload; `backend` also has an anonymous `/app/.venv` volume so the container's own virtualenv isn't shadowed by the host bind mount.

## Commands

### Via Docker Compose (repo root) — recommended
```
cp .env.example .env                          # fill in OPENAI_API_KEY at minimum
docker compose up --build                      # starts db, backend (:8000), frontend (:5173)
docker compose exec backend uv run python -m src.scripts.create_admin --email you@example.com
```
Alembic migrations run automatically on backend startup (`command:` in docker-compose.yaml).

After adding a frontend dependency, refresh the anonymous `node_modules` volume:
```
docker compose up -d --build -V frontend
```

### Backend (`backend/`, uses `uv`)
```
uv sync                                                        # install dependencies
uv run alembic upgrade head                                    # apply migrations
uv run uvicorn src.main:app --host 0.0.0.0 --port 80 --reload  # run dev server
uv run pytest                                                   # run tests (needs a reachable Postgres+pgvector; set DATABASE_URL to a *_test database)
uv run python -m src.scripts.create_admin --email you@example.com   # create/promote an admin
uv run python -m src.scripts.eval_scope                        # scope-classifier accuracy eval (needs a real OPENAI_API_KEY)
```
Tests run against a real Postgres+pgvector database (a separate `ai_tutor_test` DB is expected); they never call OpenAI — the LLM and embeddings are stubbed with LangChain fakes (`FakeListChatModel`, `DeterministicFakeEmbedding`) via dependency overrides / monkeypatching.

### Frontend (`frontend/`, uses `bun`)
```
bun install       # install dependencies
bun run dev       # start Vite dev server
bun run build     # production build
bun run lint      # run ESLint
bun run preview   # preview production build
```
No test suite is configured for the frontend. Linting uses the flat ESLint config in `frontend/eslint.config.js` (JS/JSX only, React Hooks + React Refresh plugins).

## Key design notes

- **LLM stack:** OpenAI via `langchain-openai` (`ChatOpenAI` for the main + fast models, `OpenAIEmbeddings` for embedding). Model names are env-configurable (`OPENAI_CHAT_MODEL`, `OPENAI_FAST_MODEL`, `OPENAI_EMBEDDING_MODEL`); update `.env`/`.env.example` if you change them.
- **Vector store:** `langchain_postgres.PGVectorStore` is pointed at our own Alembic-managed `chunks` table (not its auto-created default table), so foreign-key cascades stay intact. See `src/services/vector_store.py`.
- **Scope routing is an explicit classifier step**, not just a system prompt: `nodes.make_classify_node` uses structured output (`ScopeDecision`) to route `technology` / `related` / `unrelated`, with a hard-coded fallback if structured output fails. It never sees scraped page content.
- **Study plans** are built from a full outline of the technology's onboarded (ready) resources, not top-k similarity search — see `services/study_plan.py`. The LLM's resource citations are validated server-side; invalid ones are stripped and the topic is labelled "(general knowledge)".
- **Auth** is hand-rolled: argon2-hashed passwords (`pwdlib`), opaque session tokens stored hashed in the `sessions` table, sent as an httpOnly cookie. No JWT.
